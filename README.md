# RISC-V RV32I Core

A single-cycle RV32I RISC-V processor core, written in SystemVerilog and verified with directed and (soon) coverage-driven testbenches in Questa.

This project is a from-scratch build of the RV32I base integer instruction set — every module is designed, coded, and verified by hand, module by module, before being wired into the full datapath.

## Why this project exists

I'm building this to go deep on digital design and verification, the way it's actually done in industry: write RTL, write a rigorous testbench for it, prove it's correct, then move to the next block. The long-term goal is a fully pipelined core with hazard handling, branch prediction, and cache — but every stage along the way is being verified properly rather than rushed.

**Integration testbench:** `tb/rv32i_top_tb.sv` runs a hand-assembled RV32I program (`rv32i_top_program.hex`) covering every instruction category — all R-type and I-type ALU ops, LUI, AUIPC, every load/store width, all six branch types (taken and not-taken), JAL, and JALR — ending in a self-loop that acts as a halt. The program and its expected register/PC trace are generated by a small reference assembler/simulator so expected values are cross-checked against an independent model rather than hand arithmetic. Every single instruction's register write and next-PC value is checked at the cycle it retires (not just at the end), which catches a wrong result even when a later instruction reuses that same destination register. 133/133 checks pass. `instr_mem.sv` and `rv32i_top.sv` take an `INIT_FILE`/`INSTR_INIT_FILE` parameter (defaulting to `instr_mem_init.hex`) so the integration program loads independently of the existing per-module hex fixture.

**Next steps:** adopt functional coverage (SystemVerilog covergroups) and SVA assertions as standard practice for future modules, and backfill the earlier ones. So far this has only been trialed once, in `branch_comparator_tb.sv` — see "Verification approach" below for what's actually working there versus blocked.

## Verification approach

Every module has its own self-checking testbench, simulated in Questa. Testing goes beyond the obvious cases — for example, edge cases around uninitialized registers, sign-extension boundaries, and persistence of memory state after writes have all caught real bugs during development, not just confirmed the happy path.

**Coverage and assertions are being trialed, not yet standard practice across the project.** So far only `branch_comparator.sv`'s testbench has attempted either:
- **Functional coverage** — a covergroup (`cp_funct3` × `cp_taken` cross) meant to confirm all six branch types are exercised in both taken and not-taken form, not just tested once. Currently **non-functional**, not just unused — see tooling limitation below.
- **An SVA immediate assertion** — `assert (!$isunknown(branch_taken))`, checking the DUT never outputs an unknown value. This one **is active and passing** on every check.

No other testbench in the repo — including the new top-level integration testbench — uses coverage or assertions yet. Rolling both out to every module (new and existing) is a next step, not the current state.

### Known tooling limitation

This Questa Starter FPGA Edition install doesn't have the `svverification` license feature checked out, which covergroups need at simulation runtime (`vsim` fails immediately with `Unable to checkout verification license`, before any test runs). It only affects `tb/branch_comparator_tb.sv` — the only testbench that uses a covergroup — and the covergroup there is commented out for now so the rest of the testbench can run.

The directed tests and assertions don't need that license and are unaffected: `branch_comparator.sv` is fully verified — all 14 directed tests pass (BEQ/BNE/BLT/BGE/BLTU/BGEU, both taken and not-taken, plus signed/unsigned edge cases), 0 errors, 0 warnings.

For reference, if the license issue is resolved and the covergroup is switched back on, coverage is expected to come back at **100%** — the directed tests already exercise every `cp_funct3` bin (all six branch types) and every `cp_taken` outcome, so all 12 `cross_funct3_taken` bins (6 branch types × taken/not-taken) get hit.
